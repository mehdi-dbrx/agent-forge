# Plan: Mage JSON Protocol - Structured I/O for Agent Tools and Specs

> Status: PLANNED
> Created: 2026-06-17

## Context

The Mage agent relies on heuristics (keyword matching) to detect specs, free-text tool returns, and unstructured LLM output. This produces fragile behavior - spec detection fails for any domain that doesn't use "entity/function/table" vocabulary, tool returns are plain text strings the LLM has to parse, and the entire build pipeline depends on guessing.

The fix: everything is JSON. Tools take JSON in, return JSON out. Specs are JSON. The protocol is a contract, not a guess.

## The Problem (what we have now)

1. **Spec detection is a keyword heuristic** - checks for 3+ of "entit/action/function/lifecycle/table/register/booking" in the LLM response. Fails for pizza delivery, healthcare, fleet management, anything non-hotel.

2. **Tool returns are plain text** - "Procedure executed successfully (params)". The LLM has to guess what happened.

3. **Tool inputs are ad-hoc** - the system prompt describes params in prose. The LLM guesses the format.

4. **No schema validation** - nothing checks if the LLM produced valid output. Malformed specs pass silently.

## The Solution

### 1. Spec as JSON

The system prompt tells the LLM: "When you present a spec for approval, output it as a ```spec JSON block."

```json
{
  "type": "spec",
  "domain": "space pizza delivery",
  "entities": [
    {"name": "pizzas", "fields": ["pizza_id", "name", "description", "price"], "identifiers": ["name"]},
    {"name": "orders", "fields": ["order_id", "customer_name", "pizza_id", "destination", "status"], "identifiers": ["order_id", "customer_name"]}
  ],
  "actions": [
    {"name": "show_menu", "type": "function", "description": "Show available pizzas", "params": []},
    {"name": "place_order", "type": "procedure", "description": "Create a new order", "params": ["customer_name", "pizza_name", "destination"]},
    {"name": "track_order", "type": "function", "description": "Check order status", "params": ["order_id"]}
  ],
  "lifecycle": "browse menu -> place order -> track order -> receive delivery",
  "naming": {
    "schema": "main.space_pizza",
    "genie": "Space Pizza Concierge",
    "app": "space-pizza-delivery"
  }
}
```

**Detection**: code checks for ```spec fence, parses JSON, validates `type: "spec"`. Deterministic. No heuristics.

**Two layers preserved**: Magic mode user sees a human-readable summary (generated from the JSON). Author mode user sees the JSON. Internal spec stored as JSON in session.

### 2. Tool definitions as JSON files

Each tool's input schema and output schema defined in a JSON file, loaded at tool creation time.

```
conf/tools/
  show_menu.json
  place_order.json
  track_order.json
```

Example `place_order.json`:
```json
{
  "name": "place_order",
  "type": "procedure",
  "procedure": "place_order",
  "description": "Create a new pizza order for delivery",
  "params": [
    {"name": "customer_name", "type": "string", "description": "Customer's name"},
    {"name": "pizza_name", "type": "string", "description": "Name of the pizza to order"},
    {"name": "destination", "type": "string", "description": "Delivery destination (planet or station)"}
  ],
  "output": {
    "card_type": "confirmation",
    "title": "Order Placed",
    "fields": ["order_id", "customer_name", "pizza_name", "destination", "status"]
  },
  "verify_query": "SELECT * FROM {schema}.orders WHERE customer_name = '{customer_name}' ORDER BY created_at DESC LIMIT 1"
}
```

**Benefits**:
- Tool factory reads JSON, creates tools with proper schemas
- Output format defined upfront (card type, fields)
- Verify query for action tools (catches silent 0-row INSERTs)
- Generated by Mage alongside functions/procedures
- Deployed with the bundle (in conf/tools/)
- Injected into agent system prompt automatically

### 3. Tool returns as JSON

Tools return structured JSON, not plain text.

**Read tools** (functions):
```json
{"type": "result", "tool": "show_menu", "columns": ["name", "description", "price"], "rows": [...]}
```

**Action tools** (procedures):
```json
{"type": "confirmation", "tool": "place_order", "success": true, "data": {"order_id": "ORD-001", "customer_name": "Zara", ...}}
```

Or on failure:
```json
{"type": "error", "tool": "place_order", "success": false, "message": "No matching pizza found for 'Nebula Supreme'"}
```

The LLM receives structured data and can reason about it or pass it to the user as a card.

### 4. Spec as a tool call, not a text format

Text fences (```spec, ```draft_spec, XML tags) are unreliable - the LLM can ignore them. Tool calls are reliable - the LLM already produces them consistently for all other tools.

Add `present_spec` to the discovery phase tool set:

```python
async def present_spec(self, spec: dict) -> str:
    """Present the agent spec for user approval. Validates JSON schema."""
    # Validate required fields
    if not spec.get("entities") or not spec.get("actions"):
        return "Invalid spec: must include entities and actions"
    # Store spec
    self.agent.spec_presented = True
    self.agent.requirements = json.dumps(spec)
    # Return confirmation
    return "Spec presented to user for approval."
```

Flow:
1. LLM calls `present_spec(spec_json)` as a tool call
2. Tool validates JSON schema, sets `spec_presented = True`, stores spec
3. Code generates human-readable summary from JSON, shows to user
4. Magic mode: capability list. Author mode: structured spec.
5. User confirms -> `_upgrade_to_build_phase()`
6. Spec JSON fed directly to gen endpoints

No keyword matching. No text fences. No heuristics. Tool calls are the signal.

### 5. Gen endpoints receive structured spec

Instead of passing a vague domain string to gen endpoints, pass the confirmed spec JSON:

```python
# Before (vague)
exec_generate(endpoint="/api/gen/schema", body={"domain": "space pizza delivery"})

# After (structured)
exec_generate(endpoint="/api/gen/schema", body={"spec": confirmed_spec_json})
```

The gen LLM receives exact entity names, field names, action definitions. No guessing. No renaming. Discovery output = generation input.

## present_spec tool - implementation detail

```python
# In MageToolkit (discovery phase tool)

async def present_spec(self, spec: dict) -> str:
    """Present the agent spec for user approval."""
    # Validate required fields
    if not spec.get("entities") or not spec.get("actions"):
        return "Invalid spec: must include entities and actions"

    # Store spec
    self._spec_json = spec

    # Generate user-facing summary based on mode
    if self.mode == "magic":
        bullets = "\n".join(f"- {a['description']}" for a in spec["actions"])
        summary = f"Here's what your agent will do:\n\n{bullets}\n\nSound right?"
    else:
        # Author: structured view
        entities = ", ".join(e["name"] for e in spec["entities"])
        actions = "\n".join(f"  {a['name']}({', '.join(a.get('params',[]))})" for a in spec["actions"])
        summary = f"Tables: {entities}\nFunctions:\n{actions}\n\nConfirm?"

    # Send summary directly to user (not via LLM)
    await self.sse_queue.put({"event": "message", "data": {"role": "assistant", "text": summary}})

    # Return instruction to LLM: don't repeat the spec
    return "Spec presented to user. Do NOT repeat or rephrase it. Wait for their confirmation."
```

The agent loop in mage_agent.py detects when present_spec was called:
- Sets `spec_presented = True`
- Stores spec JSON in `self.requirements`
- On next user message, confirmation check runs as before

**Toolkit stores mode** at init time (passed from MageAgent).

**Revision loop**: if user says "add billing too" instead of confirming, the LLM calls present_spec again with an updated spec. Natural loop, no special handling.

**Duplicate prevention**: tool sends summary to user directly via sse_queue. Returns "do NOT repeat" to LLM. LLM shouldn't parrot the spec.

## Gen endpoint: spec via stdin

schema mode in generate_tables.py currently reads --domain from CLI args.

Change: if stdin has data, try to parse as spec JSON. If valid, use entities/fields from spec. If stdin empty or not JSON, fall back to --domain.

```python
# generate_tables.py
def mode_schema(domain: str) -> None:
    # Check stdin for structured spec
    spec = None
    if not sys.stdin.isatty():
        raw = sys.stdin.read().strip()
        if raw:
            try:
                spec = json.loads(raw)
            except json.JSONDecodeError:
                pass

    if spec and spec.get("entities"):
        # Use spec entities as table scaffolding, LLM adds types/constraints
        tables = generate_schema_from_spec(spec)
    else:
        # Original flow: LLM invents everything from domain string
        tables = generate_schema(domain)
```

Same pattern for routine_schema_generator.py - spec actions become routine scaffolding.

## Tool JSON generation step

New step in gen pipeline: after routine-provision, before prompt-generate.

```
gen-schema -> gen-data -> gen-save -> gen-provision
-> gen-routine-schema -> gen-routine-sql -> gen-routine-save -> gen-routine-provision
-> gen-tool-defs (NEW)
-> gen-prompt
-> deploy
```

New endpoint: `POST /api/gen/tool-defs`
New script: `data/gen/generate_tool_defs.py`

Reads: generated SQL files (func/*.sql, proc/*.sql) + spec JSON
Produces: conf/tools/*.json (one per tool, includes params, output, verify_query, card_type)

Merges CardMaker plan - no separate card_generator.py needed.

## Review findings

### present_spec as tool, not text fence
Tool calls are reliable. Text fences aren't. The LLM already calls tools consistently. present_spec validates JSON, sets the flag, sends the summary. No heuristics.

### Transition safety
- tool_factory.py: conf/tools/ first, config fallback
- Gen endpoints: spec via stdin, --domain fallback
- Old projects keep working

### SQL injection in verify_query
Use _escape_sql_string() for all interpolated values.

### Generator merge
Tool JSON + card defs in one file per tool. generate_tool_defs.py replaces card_generator.py.

### Duplicate message prevention
present_spec sends summary to user directly. Returns "do NOT repeat" to LLM.

### Revision loop
User says "add billing" -> LLM calls present_spec again with updated spec. Natural.
